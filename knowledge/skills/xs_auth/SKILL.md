# 登录口与账号校验逻辑审计（xs_auth）

> 来源: 用户 Codex skill `xs-auth` v0.7.0 实战沉淀（qdedu 等）,2026-08-29 迁入 xs-bigdan 知识层。
> 对 `skills/auth_bypass`(401/403 屏障绕过)互补:那个打"进不去的门",本文件打"门后的登录与账号逻辑"。
> 配套脚本: `tools/bin/slider_captcha_solver.py`(S9 滑块程序化解题)。

## 识别信号（命中即读本文件）

- 目标存在登录/注册/找回密码/改密/绑定手机邮箱等功能点
- URL/JS 关键词: `login` `register` `captcha` `verify` `token` `reset` `sms` `account`
- BRIEF 注入了测试账号（账号池战略的详细打法——登录进认证后攻击面的标准作业程序）

**定位：有流程有思路的 AI 漏洞挖掘者，不是扫描器。** 流程：先读 JS 找问题线索 → 对线索做定向验证 → 白名单查漏补缺。**主攻方向：通过绕过方式实现任意用户账号/权限接管等高价值漏洞。** 测试清单（S 章线索模式、A~F/O 章白名单、G 章复杂攻击思路）内置在本文档「测试清单」一节，随实战演进。

## 工具映射（本 skill 原为 Codex 浏览器 MCP 编写,在 xs-bigdan 中等价替换）

| 原 MCP 能力 | xs-bigdan 等价物 |
|---|---|
| `list_scripts`（列 JS 资源） | `browser_probe.py chunks <url>`（含动态 chunk 枚举,可 --save 落盘） |
| `evaluate_script`（页面执行 JS/hook fetch） | `browser_probe.py js <url> "<expr>"`（Vue hook 用 `el.__vue__.$parent` 链） |
| `network_search` / `read_network_requests` | `browser_probe.py open <url> --xhr 30 --console 20`（XHR/console 结构化输出） |
| 实际触发功能点（输错密码/请求验证码） | `browser_probe.py login <url> <user> <pass>`（mock 登录,输出后续 XHR/storage） |
| 单请求定向验证 | `xsreq.py`（第一行状态码/耗时/长度对比差异） |
| Burp 响应篡改复核 | 人工阶段（Agent 只做证据准备,标注 PENDING 交人工） |

## 适用边界（先读）

- 仅限授权目标：SRC 收录范围、教育 SRC、已获书面许可的目标。未授权立即停止。
- 默认不做大规模爆破与高频请求。弱口令测试仅按固定组合清单执行（见 B2），不扩展字典、不做批量爆破，速率 ≤2 次/秒。
- 数据口径按 `compliance-rules.md`:本地完全授权场景证据**不脱敏**;仅对外提交场景脱敏（手机号/身份证打码）。
- 目标有 WAF/风控时先了解拦截特征（HTTP 000 / 422 / 封 IP），避免打草惊蛇；确认 WAF 后遵守 SAFE MODE（methodology §0）。

## 输入

- 目标 URL、登录页 URL（BRIEF 已含）
- 测试账号（BRIEF「测试账号」节注入;多数逻辑漏洞需要登录态）
- JS 文件路径 / 授权范围说明（可选）
- 两个真实手机号（可选，用于接管类验证码测试）——**不要在会话里猜**：需要时写 `BLOCKED:VERIFY_CODE`，人工通过控制台提供后注入下一段 BRIEF

## 阶段 0：确认目标与入口

1. 确认授权范围，记录目标、开始时间。
2. 探测登录入口：主站、子域、移动端/小程序 API 是否共用同一套认证逻辑。
3. 列出目标认证相关功能点清单：登录、注册、找回密码、绑定/换绑、修改密码各在哪个入口。

## 阶段 1：浏览器辅助定位登录与账号验证 JS（起点）

用 browser_probe 在真实页面中定位：

1. `open` 打开登录页及相关功能页（注册 / 找回密码 / 个人中心-安全设置），读 XHR/console 输出记录交互请求。
2. `login` 实际触发每个功能点（输错密码登录、请求验证码），让对应 XHR/fetch 现身，锁定每类功能对应的请求与 JS。
3. 对 JS 落盘文件 grep `login`、`password`、`captcha`、`verify`、`token`、`reset`、`sms` 等关键词，定位接口与参数。
4. `chunks` 列出 JS 资源；SPA 项目先从入口 bundle 的 chunk 映射表（webpack `t.u` / jsonp）枚举模块名，按 login/auth/account/reset 等关键字猜 chunk，用 `js` 只 fetch 目标 chunk。
5. `js` hook 全局 `fetch`/`XMLHttpRequest` 记录登录流程的真实请求序列与加密参数。

产物：功能点 → JS 文件 → 接口 的映射清单。

## 阶段 2：JS 深度审计（核心阶段——找问题线索）

1. 按「测试清单」S 章「JS 分析线索模式」逐条比对定位到的 JS。
2. **优先关注可能导致任意用户接管/权限提升的线索**：验证码/校验凭证与用户解耦（不绑定用户或会话）、token 可预测或可重定向、校验步骤可跳过、校验与发送分离、重置流程参数可控等——这是主攻方向，最先处理。
3. 每条命中的线索提取证据代码片段，记录：位置、线索类型、潜在漏洞假设。
4. 梳理接口清单与完整业务流（如：发码→校验→改密），标注每步接口、参数、会话标识。
5. 把线索组织成攻击链：单一线索往往不够，思考组合（如 前端校验 + 弱随机数 → 完整绕过）。G 章复杂攻击思路库中已有的思路按条目直接执行。

**产物（契约强制）**：可疑点清单 + 接口清单写入 `evidence/_endpoint_params.json`（复用 js_analysis 契约格式,含 method/params/auth/source_files）——让值池联动引擎自动消费你审计出的接口;可疑点另存 `evidence/` 并在 digest 疑似点节引用。

## 阶段 3：可疑点定向验证（核心验证——不是扫描）

1. 针对每个可疑点设计专门验证方案：有目的的单个/少量请求，不是批量遍历。
2. **接管类验证先走 BLOCKED**:当可疑点涉及"任意用户接管"（验证码跨用户/跨会话可用、可重定向、重置流程可指定接收方）时,输出 `### BLOCKED`（type: VERIFY_CODE,需要: 两个真实手机号及用途说明）,暂停等人工。人工提供后线索注入下一段 BRIEF;用户未提供时该线索标记「需人工复核」，不强行推进。
3. 每项验证记录：请求、响应、正常/异常差异对比（`xsreq --save` 落 evidence）。
4. 判定：成立 / 不成立 / 需人工复核。不成立的记录原因后即翻篇，不纠缠。
5. 验证成立的即按「证据落盘协议」写 evidence/ 文件并打印 FINDING 行，进入报告阶段。

## 阶段 4：白名单查漏补缺

1. 定向验证完成后，检查「测试清单」白名单（B~F、O 章）哪些项尚未覆盖。
2. 未覆盖的项低频率补测；未列入白名单的一律不测。
3. 所有测试低频率进行；命中封禁特征立即暂停并换策略（**等待即烧钱**:锁定/冷却场景禁止等待,写 BLOCKED 或换面）。

## 阶段 5：报告输出

每个确认的漏洞按 xs-bigdan「证据落盘协议」输出：`evidence/NN-<漏洞名>.txt`（标题/复现请求/关键响应/影响）+ 会话打印 `FINDING: <类型>|<标题>|<证据文件>|CONFIRMED`，提交前人工复核：

- 标题：漏洞类型 + 位置（如「找回密码验证码跨账号复用导致任意用户接管」）
- 复现步骤：从登录页开始的可复现路径
- 证据：关键请求/响应，含正常与异常响应差异对比；线索来自 JS 的附代码片段（脱敏口径见适用边界）
- 影响：能造成什么后果（任意用户账号接管 / 权限提升 / 撞库），对照 `references/rating-standard.md` 评估
- 修复建议：一句到两句可落地的修复方案

## 测试清单（内置，随实战演进）

### S. JS 分析线索模式（阶段 2 比对用）

- S1 前端校验：密码复杂度/验证码/流程步骤仅在前端 JS 判断 → 服务端不校验 → 测：跳过前端直接调接口
- S2 密钥/私钥硬编码：RSA 私钥、AES/SM2/SM4 key、盐值写在 JS → 可解密流量/伪造签名 → 测：解密登录参数、伪造 token
- S3 弱随机数：token/验证码/票据用 Math.random()、Date.now()、递增序列生成 → 可预测 → 测：预测并提前构造
- S4 客户端信任字段：success/status/step/role/level 等字段决定前端流程或权限展示 → 响应篡改/参数篡改 → 对应白名单 B3
- S5 硬编码凭据/调试入口：测试账号、后门接口、debug=true、隐藏配置项 → 直接利用或信息泄露
- S6 敏感信息泄漏：console.log、错误响应、注释暴露 token/密钥/内网地址/用户数据 → 收集为漏洞证据
- S7 可逆加密/混淆：自定义加密、base64、简单替换 → 还原明文 → 测：还原后分析参数结构找可控点
- S8 动态执行：eval/new Function/动态拼接 URL 或查询 → 潜在注入点 → 按白名单相关项定向测试
- S9 滑块验证码客户端加密可复刻：验证码坐标由前端加密提交（AES/SM4-ECB+PKCS7 常见，CryptoJS 风格），密钥随验证码响应下发（secretKey）→ 图像模板匹配（拼图 alpha 蒙版滑动比对）求缺口 + 复刻加密 → 测：程序化生成 captchaVerification 调业务接口，确认是否单次消费、是否可绕过登录风控/发码防刷（配套脚本：`tools/bin/slider_captcha_solver.py`，用法见「工具参考」）
- S10 加密错误信息泄漏：响应报 "Input length must be multiple of 16 when decrypting with padded cipher" / "Given final block not properly padded"（CryptoJS 异常透传）→ 确认算法族与模式（AES-128-ECB 等）→ 用于精确复刻加密实现
- S11 绑定/存在状态枚举口：发码、重置、token 等端点对「未绑定/登录名不存在」返回独立错误码（如 23009/201129/2011124）→ 响应差异即枚举 → 测：逐个端点确认是否免验证码、是否限速；token 端点类免验证码枚举口优先级最高（可批量）
- S12 前端 mock 登录（纯前端鉴权）：登录逻辑全在前端实现——Vuex `_login` 硬编码 SET_TOKEN 固定值、`_getInfo` 返回固定角色、路由守卫仅查 token 是否存在，无真实后端登录接口 → 任意伪造 token 可进后台 → 测：登出后手动写入任意 token（localStorage.setItem）直跳受保护路由，确认路由守卫是否仅查存在性；纯前端滑块验证可经 el.__vue__.$parent 链定位 onSuccess 方法直接调用绕过（对应白名单 B3）

### A. 信息收集与逻辑梳理（必做前置，非漏洞测试）

- A1 接口清单：登录/注册/发码/校验/找回/改密/绑定全量枚举
- A2 JS 加密分析：密钥硬编码、前端可逆、算法识别（RSA/AES/SM2/SM4）
- A3 会话机制：cookie/JWT/自定义头，校验在服务端还是前端
- A4 Token 生成：时间戳/固定值/可预测/随机数是否安全
- A5 登录态传递：header/body/cookie 中哪些字段被服务端信任，能否被篡改

### B. 登录绕过（白名单）

- B2 弱口令组合验证：按固定组合清单逐一尝试（不批量、不扩展字典）。**速率 ≤2 次/秒;单账号连续失败 2-3 次立即换下一账号（防锁号）;命中即记录证据并停止后续组合;触发锁定 → BLOCKED,禁止等解禁。**

### C. 双因子/多因子绕过（暂时移除）

已暂时移除：AI 对双因子绕过类漏洞的理解不足，不足以支撑挖掘，待思路成熟后再回归。相关复杂思路可先沉淀到 G 章，由用户确认后测试。

### D. 找回密码/改密逻辑（白名单）

- D1 步骤参数篡改：step/userid/uid 参数可改，跳过中间步骤
- D2 校验 token 缺陷：token 在 URL/响应/Referer 泄露、不绑定用户、可预测、不过期、位数短可爆破
- D3 密保问题：问题/答案仅前端校验、答案可爆破（生日/固定选项）
- D4 改密后旧凭证：旧会话仍有效、其他设备不失效、session 不轮换
- D5 校验与发送分离：可修改接收方参数（发给自己验别人的码）、短信/邮箱校验可绕过

### E. 账号绑定（白名单）

- E1 换绑：绑定手机/邮箱无二次验证、换绑后旧凭证仍可用

### F. 会话与 Token（白名单）

- F1 JWT：算法混淆（none/HS256→RS256）、密钥弱、exp 缺失、签名不校验
- F2 Token 泄漏：日志/响应包/Referer/前端明文存储、URL 传递

### O. OAuth/SSO 授权逻辑（白名单）

- O1 redirect_uri 校验缺陷：redirect_uri 白名单缺失或可绕过（只校验前缀/包含、参数污染、URL 解析器差异、双写编码）→ 授权码可被攻击者截获 → 测：尝试在授权请求中替换 redirect_uri 为攻击者域，观察 code 是否下发
- O2 state 缺失/固定：授权流程无 state 或 state 固定/可预测 → 登录 CSRF（受害者被绑定到攻击者账号）→ 测：对比两次授权请求的 state 是否随机变化；无 state 时记录登录后归属
- O3 授权码/凭证复用：code 不过期、可重放、不绑定 client_id/redirect_uri → 测：code 使用两次、换 client/redirect_uri 重放，观察是否二次换 token 成功
- O4 社交登录 code 校验缺陷：第三方登录 code 换取接口不校验 code 与当前用户的绑定一致性（code 与账号解耦）→ 任意账号接管 → 测：用 A 账号流程获取的社交 code 在 B 账号流程中换取 token（需两个测试账号；涉及接管先走阶段 3 BLOCKED 流程）
- O5 scope/权限提权：授权请求中 scope 参数可控且服务端不校验 → 申请超范围权限（如 userinfo 扩展字段、管理接口）→ 测：在授权请求中修改/追加 scope，观察返回的 token 权限
- O6 客户端凭据硬编码/泄露：client_id + client_secret（如 Basic web:qdedu 风格）硬编码在前端 JS 或可被提取 → 冒充合法客户端调用 token 接口 → 测：用提取的凭据直接调 /token 端点，确认是否可独立换取 token
- O7 正面项（非漏洞，报告记录）：redirect_uri 严格白名单、state 每次随机且校验、code 单次消费且绑定用户、token 端点限速 —— 这些项验证后记录为「安全正面项」，不作为漏洞提交

### G. 复杂攻击思路库（高价值，最高优先级）

说明：复杂漏洞思路的镶嵌位置。用户学到/想到的复杂攻击思路按下方模板写成条目后，AI 必须按条目逐步执行，优先级高于白名单。未入库的复杂思路不主动测（用户临时提供并确认的除外）。新条目登记到文末登记表。

条目模板：

- 思路名：
- 适用场景：
- 前置条件：
- 攻击链步骤：（按顺序的请求/操作，写明接口、参数、修改点）
- 验证方法：
- 判定标准：（什么样的响应/状态 = 漏洞成立）
- 风险级别：

示例条目（演示格式，可删除）：

- 思路名：找回密码验证码跨账号复用（示例）
- 适用场景：找回密码流程存在"校验与发送分离"或"验证码不绑定会话"嫌疑
- 前置条件：两个真实手机号 A、B；A 手机号在目标有注册账号
- 攻击链步骤：① 用 A 手机号发起找回密码，收到验证码 ② 用 B 手机号发起找回密码 ③ 在 B 的流程中提交 A 收到的验证码 ④ 观察是否进入重置密码步骤
- 验证方法：走完①~④，对比 B 流程正常校验与提交 A 验证码的响应差异
- 判定标准：B 的流程用 A 的验证码校验通过并进入重置步骤 = 漏洞成立（任意用户接管）
- 风险级别：高
