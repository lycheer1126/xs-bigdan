# 漏洞报告编写技能（中文 SRC 提交版）

> 来源：目标 SRC 报告写作风格与平台五段式模板提炼。
> 目标：审核人员**仅凭报告即可独立复现**，证据链完整、可直接放行/定级。
> 本技能在 report 阶段读取；证据协议（发现过程/危害放大节）在 system.md 证据落盘协议中约定。

---

## 一、何时使用

- 任务收尾要把 findings + evidence 组织成可提交报告；
- 或单个漏洞的证据齐全、要按 SRC 平台口径整理成五段式正文。

## 二、报告结构（五段式主模板）

```
【标题】[系统/平台名]存在[漏洞类]，[最大危害一句话]

一、漏洞摘要【必填】
二、受影响资产【必填】
三、复现手册【必填】（报告主体，占 ~80%）
四、风险影响评估【必填】
五、修复建议【必填】
```

平台自带官方模板时优先沿用平台章节名，本结构与之兼容。

### 标题规范
- 句式：`[资产/系统] + 存在 + [漏洞类] + ， + [攻击者能做什么/最大后果]`
- 例：` exhibitor.cantonfair.org.cn 存在未授权访问，可分页导出全量 21.4 万参展商企业库（含联系人手机邮箱）`
- 直接上最高危影响，不绕弯。

### 一、漏洞摘要（1~2 句讲完五要素）
**哪个系统 + 哪个端点 + 什么漏洞 + 能拿到什么/能做什么 + 影响规模**。
- 句式："XX 平台存在 XX 漏洞，可 XXX（未授权读取/接管/批量枚举），导致 XXX 泄露/业务 XX。"
- 用"仅凭 xxx 即可…"突出易利用性；多个同源端点合并表述。

### 二、受影响资产
- 直接列**具体端点**（域/完整 URL/接口路径），一个一行；不写无关内容。

---

## 三、复现手册【黄金攻击链】（核心）

每篇报告按同一条叙事链写，每步 = **动作 → 结果 → 证据(URL/raw 包/〔图〕)**，不写空话：

```
① 发现过程     → 从哪个页面 → 加载哪个 JS → 扒出网关/接口契约 → 定位漏洞点
② 防御证据     → 直接调接口 401/403 → 证明"本来有校验"（最能加分，有则必写）
③ 构造请求     → 完整 raw 数据包（可直接重放，请求包即可）
④ 验证成功     → 响应里的关键敏感字段/成功标志
⑤ 危害放大     → 遍历/批量/全量证明——不是偶发一条（定级关键）
⑥ 收尾合规     → 固定措辞声明测试边界
```

### 各步要点

**① 发现过程（信息收集起点 + JS 分析）**：写清资产从哪来、**从哪个 JS 文件**（带完整 URL）扒到了什么——
网关前缀/真实后端、AppId/请求头约定、接口契约、签名算法/密钥材料。这正是 xs-bigdan recon/linkage
的常规产物（契约表/JS 分析），照抄即可。没留过程时按证据中 URL 的路径特征合理补全来源叙述。

**② 防御证据**：先演示"正常被拒"（401/403/权限认证失败）再给绕过——证明不是目标裸奔而是可绕过/漏配。
绕过根因一句话讲清："仅校验 Authorization 非空 → 带任意非空值即过"、"白名单只判断包含 → `#`/`@` 绕过"、
"公钥当认证、公钥随客户端下发 → 人人可离线伪造"。

**③ 数据包规范（报告中最高优先级）**：
1. **raw 请求包全量贴出**，保持原始格式，关键头一个不省（Authorization/签名头/Tenant-Id 等）；
2. 方法/路径/Host/headers/空行/body 对齐 HTTP 原样；**POC 不用 curl，用完整数据包**（只请求包，不带响应包）；
3. 有签名/加密/时间戳计算的，附一行可直接复跑的 `python -X utf8 -c "..."` 并注明输出字段对应关系；
4. 复杂利用给脚本文件并说明运行方式与预期输出。

**⑤ 危害放大（决定定级）**：论证"不是偶发，而是全量/可遍历/实时"——userId/工号/orgId 递增遍历附批量包、
全量清单接口、写操作能力（配合三性评估）。善用**有依据的量化词**："所有/全量/实时/无需凭证"，宁少说勿虚报。

**⑥ 收尾合规（必写）**：模板句——
- "因合规测试，此处只进行了可读证明，实则该参数还可用于 XX 写操作（未实际调用）。"
- "相关数据已做脱敏/掩码处理；测试账号与凭据已还原。"
- xs-bigdan 场景固定补一句："本次测试共验证不超过 5 条数据记录，未进行批量导出/写操作。"

### 复杂漏洞加两节
业务链路长/牵扯多套系统时，复现手册开头补：**业务背景**（系统干嘛的、数据怎么流转）+
**漏洞成因分条**（1. 2. 3. 列 root cause 与判断依据，每条给证据来源）。

## 四、图位占位规约

**不需要真的插入截图**：需要图的地方插统一占位符，说明该截什么图，交由提交者补图：

```
〔图1〕此处放图：目标站点登录页（证明系统真实在跑）
〔图2〕此处放图：JS 中定位到网关前缀与 AppId 的代码段
```

- 每个图位**必须写清期望截图内容**，不能只写"截图"；
- 开头注明："文中〔图n〕为占位标记，请按说明截图后替换。"
- 默认图位清单（按攻击链序）：①首页/登录页 ②JS 关键常量段 ③401/403 被拦报错 ④绕过后响应含敏感字段
  ⑤遍历/批量数据列表 ⑥危害落地物（下载的文档/导出文件）。

## 五、各漏洞类型复现骨架（速查）

| 漏洞类型 | 复现链要点 |
|---|---|
| 未授权访问/信息泄露 | 资产→JS/接口契约→**不带凭证直接调**→响应含数据→批量证明 |
| 认证/权限绕过 | 先演示"正常被拒"→讲绕过原理（仅判空/固定头/畸形请求）→给绕过后的包 |
| IDOR/越权 | 正常调用（低权/本人）→换 id 读他人数据→说明可遍历 |
| URL 跳转 | 正常跳转→指出白名单校验缺陷（包含判断/`#`/`@`/双写）→payload 成功跳 evil |
| 任意文件上传 | 拿 OSS policy/signature→替换→上传→访问落地 URL→论证钓鱼/存储 XSS |
| Swagger/API 泄露 | 发现单点→枚举全部模块→列出未鉴权可打接口 |
| 高权限接管/复杂链 | 五段式 + 业务背景 + 漏洞成因分条 + 影响面（多环境同源） |

## 六、风险影响评估（三性）

从三性分角度列点，句式 = "攻击者可…→ 真实业务后果 → 规模"：
- **机密性**：泄露哪些敏感数据、是否全量、是否可遍历/实时；
- **完整性**：能否写/改/伪造（伪造合同/篡改配置）→ 业务后果；
- **可用性**：业务中断/恶意跳转钓鱼/账号接管。

## 七、修复建议

**原理性修复**，非"加 WAF 规则/封 IP"式临时规避。简单漏洞一句；复杂漏洞分条：
认证改造 → 授权拦截（归属校验）→ 最小权限 → 审计告警。

---

## 八、文风自检 + 提交前 Checklist

- 精简技术流：URL/数据包/代码说话，动作→结果→证据；
- 保留"排查过程"：失败的尝试值得写一两句，证明限制真实存在；
- 关键判定给依据；编号步骤、一步一图位；不写空泛形容词与无来源夸大。

- [ ] 标题：系统 + 漏洞类 + 最大危害一句话
- [ ] 摘要含五要素
- [ ] 受影响资产是具体可访问 URL/接口
- [ ] 复现手册每步有证据（URL/raw 包/〔图〕）
- [ ] raw 包完整、关键头齐全、可重放；签名类附可复跑命令
- [ ] 图位写清"该截什么图"
- [ ] 有合规边界说明
- [ ] 三性写全、量化词有依据
- [ ] 修复建议为原理性
